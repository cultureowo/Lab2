# Лабораторна робота №2: Клієнтський застосунок управління бібліотекою

## Тема та Мета
- **Тема**: Розробка клієнтського застосунку управління бібліотекою.
- **Мета**: Розробити клієнтський застосунок для управління бібліотекою, який дозволяє вести облік книг та користувачів, а також здійснювати операції з позичання та повернення книг. Програма реалізована з використанням можливостей TypeScript (класи, інтерфейси, generics, модулі, простори імен `namespace`).

## Реалізований функціонал

1. **Ізольована розмітка**: `index.html` містить виключно `<div id="app"></div>`. Весь інтерфейс будується програмно за допомогою DOM API.
2. **Типізація та ООП**:
   - `IBook`, `IUser`, `Identifiable` — суворі TypeScript-інтерфейси.
   - Класи `Book` та `User` інкапсулюють стан із приватними полями, публічними гетерами, сетерами та методами (`borrow()`, `returnBook()`, `canBorrow()`, `addBorrowedBook()`).
   - Generic-клас `Library<T>` забезпечує роботу з довільними колекціями сутностей, що мають `id` (додавання, видалення, пошук, фільтрація, пагінація).
   - Простір імен `namespace Validation` містить правила валідації полів (обов'язковість, числовий ID, регулярний вираз для року випуску книги).
3. **Облік книг та користувачів**:
   - Позичання книги із запитом ID через кастомне модальне вікно.
   - Ліміт: не більше 3-х книг на одного користувача (при спробі взяти 4-ту виводиться модальне попередження).
   - Повернення книги зі зміною статусу та оновленням лічильника користувача.
   - Пошук книг за назвою або автором у реальному часі.
   - Пагінація списку (по 5 елементів на сторінку).
   - Видалення книг та користувачів (із захистом: користувача з неповерненими книгами видалити не можна).
4. **Збереження даних**: Всі зміни автоматично синхронізуються у `LocalStorage` через клас `Storage`.
5. **Система сповіщень**: Реалізовано кастомне модальне вікно `Modal.ts` — використання нативного `alert()` повністю виключено.

## Відповіді на контрольні питання

### 1. Які переваги дає використання TypeScript порівняно зі звичайним JavaScript при розробці великого застосунку?
- **Статична типізація**: Виявлення помилок (неправильні типи аргументів, звернення до неіснуючих властивостей, помилки в назвах) ще на етапі написання коду та компіляції, а не в runtime у клієнта.
- **Покращений автодоповнення та рефакторинг**: IDE має повну інформацію про сигнатури методів та структуру об'єктів, що дозволяє безпечно перейменовувати методи, властивості та знаходити всі їхні використання.
- **Самодокументований код**: Типи та інтерфейси є контрактами, що полегшує онбординг нових розробників та роботу в команді.

### 2. У чому різниця між класом та інтерфейсом у TypeScript? Наведіть приклад, коли варто використати саме інтерфейс.
- **Інтерфейс (`interface`)**: Існує тільки на етапі компіляції TypeScript і повністю видаляється під час компіляції в JavaScript (не додає байтів у фінальний бандл). Не містить реалізації, а лише описує форму (контракт) об'єкта.
- **Клас (`class`)**: Є повноцінною конструкцією JavaScript (ES6+), яка залишається у скомпільованому коді, містить конструктор, поля, реалізацію методів і може бути інстанційована через `new`.
- **Приклад використання інтерфейсу**: Опис форми даних від сервера або об'єкта з `LocalStorage` (наприклад, `IBook`, `IUser`), де потрібен лише контракт без реалізації методів.

### 3. Що таке Generics і навіщо вони використані саме в класі Library? Що було б втрачено, якби Library не був узагальненим (generic)?
- **Generics (узагальнення)** дозволяють створювати компоненти, функції та класи, які працюють з різними типами даних, зберігаючи строгу типізацію та безпеку типів без використання `any`.
- У класі `Library<T extends Identifiable>` generic дозволяє використовувати одну й ту саму логіку колекції (додавання, видалення, пошук, пагінація) як для `Book`, так і для `User`, чи будь-яких інших сутностей.
- Якби `Library` не був generic, довелось би або дублювати код (`BookLibrary`, `UserLibrary`), або використовувати `any`, втрачаючи перевірку типів та автодоповнення.

### 4. Поясніть різницю між модулями (ES-модулями) та просторами імен (namespaces) у TypeScript. Коли доречно використовувати namespace всередині модуля?
- **ES-модулі (`import` / `export`)**: Сучасний стандарт JavaScript. Файли мають власну область видимості, залежності підключаються явно, підтримують tree-shaking та статичний аналіз.
- **Простори імен (`namespace`)**: Специфічна конструкція TypeScript (раніше відома як внутрішні модулі) для логічного групування пов'язаних функцій та констант під одним глобальним або експортованим об'єктом.
- **Доречність всередині модуля**: Коли в межах одного файлу потрібно згрупувати споріднені чисті функції валідації або службові утиліти, наприклад `Validation.isValidUserId()` та `Validation.isValidYear()`, не засмічуючи простір імен файлу.

### 5. Як організована модульна структура проєкту (models, services, utils)? Яку відповідальність несе кожен із цих шарів?
- `models/`: Відповідає за структури даних та сутності предметної області (`Book`, `User`, `IBook`, `IUser`). Містить гетери/сетери, валідацію внутрішнього стану та серіалізацію (`toJSON`). Нічого не знає про DOM або UI.
- `services/`: Містить бізнес-логіку застосунку (`Library<T>`, `Storage`, `NotificationService`). Керує збереженням, колекціями, правилами взаємодії між книгами та користувачами.
- `utils/`: Чисті службові функції (`validators.ts`, `idGenerator.ts`), які не мають побічних ефектів і легко тестуються.
- `ui/`: Єдиний шар, що взаємодіє з браузерним DOM, монтує елементи та обробляє користувацькі події (кліки, введення, форми).

### 6. Як реалізовано збереження та відновлення даних через клас Storage і LocalStorage? Які обмеження має LocalStorage як сховище даних?
- Реалізовано через статичні методи `Storage.get<T>()`, `Storage.set<T>()`, `Storage.remove()` та `Storage.clear()`, які обгортають виклики `localStorage.getItem` та `JSON.parse` / `JSON.stringify` у блоки `try...catch`.
- **Обмеження LocalStorage**:
  - Ліміт об'єму зазвичай близько 5–10 МБ на домен.
  - Синхронний API, що може блокувати головний потік при великих обсягах даних.
  - Зберігає лише рядки (потрібна серіалізація та десеріалізація JSON).
  - Дані доступні лише на поточному пристрої та в поточному браузері.

### 7. Опишіть логіку методів позичання (borrow) та повернення (return) книги. Які стани книги вони змінюють і як це відображається в UI?
- **Позичання (`borrow(userId)`):**
  - Перевіряє `!isBorrowed`. Встановлює `isBorrowed = true`, записує `borrowedBy = userId` та поточну дату `borrowDate`.
  - У користувача викликається `user.addBorrowedBook(book.id)`.
  - У списку книг замість синьої кнопки «Позичити» з'являється помаранчева кнопка «Повернути» та бейдж «Позичено: [ID користувача]».
- **Повернення (`returnBook()`):**
  - Перевіряє, що книга була позичена. Встановлює `isBorrowed = false`, `borrowedBy = null`, `borrowDate = null`.
  - У користувача викликається `user.removeBorrowedBook(book.id)`.
  - У списку книг знову відображається кнопка «Позичити».

### 8. Як реалізована валідація форм (обов’язкові поля, id користувача, рік видання)? Яким чином регулярний вираз перевіряє коректність року?
- Реалізована через функції `Validation.validateBook` та `Validation.validateUser`.
- Обов'язковість перевіряється методом `Validation.isNotEmpty(str)`.
- ID користувача перевіряється регулярним виразом `/^\d+$/` (дозволені виключно цифри).
- Рік видання перевіряється регулярним виразом `Validation.YEAR_REGEX = /^(1[0-9]{3}|20[0-2][0-9]|2030)$/`, який переконується, що рядок складається рівно з 4 цифр у діапазоні від 1000 до 2030 року, після чого додатково перевіряється числове обмеження відносно поточного року.

### 9. Яке обмеження накладено на кількість одночасно позичених книг одним користувачем і як застосунок повідомляє про перевищення ліміту?
- Максимум **3 книги** на одного користувача (`User.MAX_BORROW_LIMIT = 3`).
- Метод `user.canBorrow()` повертає `false`, якщо в списку позичених книг уже є 3 елементи.
- При спробі позичити 4-ту книгу `NotificationService.showLimitExceeded()` показує кастомне модальне вікно: *«Користувач [Ім'я] ([ID]) вже позичив 3 книги! Кожен юзер може позичити не більше 3-х книг.»* із кнопкою «Зрозуміло!».

### 10. Чому в цій роботі заборонено писати декларативну розмітку в index.html, і як натомість генерується DOM-структура застосунку?
- Заборона введена з навчальною метою: для глибокого розуміння роботи браузерного DOM API, об'єктно-орієнтованого підходу у фронтенд-розробці та того, як сучасні фреймворки (React, Angular, Vue) програмно рендерять інтерфейс.
- Структура генерується через виклики `document.createElement()`, присвоєння `className`, атрибутів `dataset`, методів `appendChild()` та обробників подій `addEventListener()`, інкапсульованих у класи компонентів (`BookForm`, `BookList`, `UserForm`, `Modal`).

### 11. За що відповідає webpack.config.js у проєкті? Назвіть щонайменше три ключові налаштування, які ви виконали самостійно.
1. `entry`: Вхідна точка збірки (`./src/index.ts`).
2. `output`: Параметри вихідного бандла (`path`, `filename: 'bundle.[contenthash].js'`, `clean: true`).
3. `module.rules`: Правила завантаження файлів (`ts-loader` для `.ts`, комбінація `style-loader`, `css-loader`, `postcss-loader` для `.css`).
4. `devServer`: Налаштування локального сервера для розробки (порт 9000, hot reload, обслуговування статики).

### 12. Яку роль виконують ESLint та Prettier у проєкті та в чому принципова різниця між їхніми задачами?
- **ESLint**: Статичний аналізатор коду (лінтер). Його мета — пошук потенційних помилок, антипатернів, невикористаних змінних, порушень типів та дотримання стандартів мови.
- **Prettier**: Інструмент автоматичного форматування коду. Його мета — суто візуальний вигляд (відступи, лапки, крапки з комою, максимальна довжина рядка).
- **Різниця**: ESLint відповідає за якість і правильність логіки коду, а Prettier — за єдиний стиль його оформлення.

### 13. Що тестують юніт-тести для класів Library та Validation за допомогою Mocha? Наведіть приклад тест-кейсу для одного з методів.
- Для `Library<T>`: початковий стан, додавання елементів, виявлення помилок при додаванні елемента без `id`, пошук за `id`, видалення елемента, фільтрація за предикатом, пагінація.
- Для `Validation`: перевірка обов'язкових полів (`isNotEmpty`), числовий формат ID (`isValidUserId`), валідність року (`isValidYear`), валідація об'єктів книг і користувачів.
- **Приклад тест-кейсу**:
  ```typescript
  it('should reject non-numeric characters in user ID', () => {
    expect(Validation.isValidUserId('user123')).to.be.false;
    expect(Validation.isValidUserId('12-34')).to.be.false;
  });
  ```

### 14. Як працює Husky pre-commit hook у цьому проєкті і яку проблему він вирішує в командній розробці?
- Husky перехоплює подію `git commit` і автоматично виконує скрипт `.husky/pre-commit` (запуск `npm run lint` та `npm run test`).
- Якщо хоча б один тест падає або компілятор TypeScript знаходить помилку, коміт скасовується.
- **Проблема, яку він вирішує**: Запобігає потраплянню битого чи невідформатованого коду в спільний репозиторій команди (CI/CD залишається зеленим).

### 15. У чому основні відмінності між webpack та Vite — за швидкістю запуску dev-сервера, налаштуванням конфігурації та розміром продакшн-збірки?
- **Швидкість старту**: Vite стартує майже миттєво (50-200 мс) без початкового бандлінгу завдяки нативному ESM; Webpack мусить спочатку скомпілювати всі файли в пам'яті.
- **Налаштування**: Vite працює «з коробки» для TypeScript та сучасного CSS без потреби встановлювати та зв'язувати 5-6 додаткових лоадерів, як це потрібно у Webpack.
- **Продакшн-збірка**: Vite використовує Rollup з ефективним tree-shaking та esbuild для мініфікації, генеруючи чистіші та компактніші бандли швидше, ніж стандартна збірка Webpack.
